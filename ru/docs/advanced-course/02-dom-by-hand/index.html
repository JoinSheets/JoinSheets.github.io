1. Теория

Документ как дерево

Браузер хранит открытую страницу не как текст, а как дерево объектов — Document Object Model, DOM. Корень дерева — объект document; его потомки — узлы разных типов: элементы (<div>, <span>, <td>, …), текстовые узлы (содержимое между тегами) и несколько более редких видов (комментарии, инструкции обработки). У каждого узла есть parentNode, список childNodes, и числовое поле nodeType, по которому эти виды различаются программно: 1 — элемент (Node.ELEMENT_NODE), 3 — текст (Node.TEXT_NODE), 8 — комментарий (Node.COMMENT_NODE), 9 — сам документ (Node.DOCUMENT_NODE). HTML-разметка, которую парсит браузер, — это один из способов описать такое дерево текстом; но дерево существует и тогда, когда ни один символ HTML не отображается, — именно с ним работает JavaScript через DOM API.

Построить фрагмент этого дерева можно напрямую, вызов за вызовом:

var row = document.createElement('tr');
var cell = document.createElement('td');
cell.className = 'del';
cell.setAttribute('title', 'удалено (DELETE)');
cell.appendChild(document.createTextNode('∅'));
row.appendChild(cell);

Этот код работает и в нём ничего не скрыто — именно так DOM устроен «снизу». Но у него есть неудобство, которое становится критическим с ростом глубины дерева: структура результата (узел row, в нём cell, в cell — текст) нигде не видна целиком — она размазана по последовательности императивных присваиваний, и чтобы восстановить её в голове, нужно мысленно проиграть все строки по порядку. Вложенность в разметке (<tr><td>∅</td></tr>) и вложенность в коде, который эту разметку строит, — две разные вещи, и с каждым дополнительным уровнем расхождение между ними становится болезненнее.

Паттерн hyperscript: дерево как один вызов функции

Решение, к которому разные команды независимо друг от друга пришли в середине 2010-х, устроено просто: описать дерево одним вызовом функции, где вложенность вызовов совпадает с вложенностью результата. Библиотека с буквальным названием hyperscript (2014) задала распространённый с тех пор вид сигнатуры — h(tag, props, children) — и имя h, которое затем переняли Mithril (m(selector, attrs, children)), Snabbdom и построенный на нём Vue 2’s render-функции (h(tag, data, children)), Preact и другие. React пришёл к той же форме не копированием, а конвергентно: React.createElement(type, props, ...children) решает ровно ту же задачу, и JSX, вопреки распространённому впечатлению, не альтернатива этому подходу, а лишь синтаксический сахар над ним, — <div className="x">{children}</div> транслируется babel’ом именно в вызов React.createElement('div', {className: 'x'}, children) до того, как код доберётся до браузера.

Сравните сигнатуры трёх независимых реализаций одной идеи:

// hyperscript (библиотека, 2014)
h('div.warning', { title: 'осторожно' }, 'текст')

// Mithril
m('div.warning', { title: 'осторожно' }, 'текст')

// React.createElement — та функция, в которую компилируется JSX
React.createElement('div', { className: 'warning', title: 'осторожно' }, 'текст')

Разница в деталях (где класс — часть селектора строкой, где отдельным полем объекта) не меняет сути: в каждом случае дерево DOM описывается вложенностью вызовов, а не последовательностью мутаций уже существующих узлов.

util.js::el(tag, attrs, ...children) — член той же семьи, написанный вручную, без JSX и без шага трансляции:

el('td', { class: 'del', title: 'удалено (DELETE)' }, '∅')

Эта строка строит в точности тот же фрагмент, что императивный код пятью строками выше — но вложенность вызовов el() теперь совпадает со структурой результата буквально, один к одному, что и было целью всего паттерна. Обращение именно к ручной реализации, а не к одной из готовых библиотек выше — прямое следствие ограничения из главы 1: без шага сборки компилировать JSX негде, а готовые библиотеки хотя и доступны как обычный <script>, добавляли бы внешнюю зависимость, которую проект принципиально не принимает.

Атрибут и свойство: две истории одного и того же узла

У DOM-узла одновременно существуют атрибуты — то, что буквально написано в исходном HTML-тексте, доступное через getAttribute/setAttribute и всегда представленное строкой, — и свойства JS-объекта node, такие как node.value или node.checked, которые могут быть любого типа. Эти две вещи исторически не одно и то же, и расхождение между ними — не недосмотр, а следствие того, как DOM развивался.

Спецификация DOM первого уровня (1998 год) описывала HTML как дерево, максимально близкое к тексту разметки: атрибуты хранились как пары «имя — строка», напрямую отражающие то, что написал автор страницы. Когда страницы стали интерактивными, этого представления стало недостаточно: пользователь, печатающий в поле ввода, меняет состояние, которого в исходной разметке никогда не было и не могло быть. Ответом стали «IDL-атрибуты» — они же свойства JS-объекта узла — живое, типизированное отражение текущего состояния, не обязанное совпадать с тем, что когда-то было написано в тексте. Для большинства пар браузер синхронизирует одно с другим в обе стороны (атрибут class и свойство className) — но именно там, где состояние способно меняться независимо от разметки, синхронизация становится односторонней. Поле ввода — самый наглядный случай: <input value="draft"> задаёт лишь начальное значение (технически это ложится на свойство defaultValue); как только пользователь начинает печатать, меняется только .value, а исходный атрибут остаётся прежним. Расхождение тут не случайно, а намеренно — именно оно позволяет кнопке «Reset» в HTML-форме восстановить поле к тому, что было изначально написано в разметке, а не к тому, что успел напечатать пользователь: без разделения «исходное значение» / «текущее значение» такой кнопке было бы попросту не на что ссылаться.

Та же логика стоит за так называемыми булевыми атрибутами HTML (disabled, checked, selected, readonly): для них важен сам факт присутствия атрибута в разметке, а не его текстовое значение — <button disabled="false"> всё равно задаёт отключённую кнопку, потому что спецификация читает такие атрибуты как «есть/нет», а не как булеву строку. el() следует этому правилу напрямую: ветка if (v === true) node.setAttribute(k, '') ставит атрибут пустой строкой, а не текстом "true", — ровно то представление, которого ожидает браузер для булевых атрибутов, и ровно то, что отличает их от любого другого атрибута со значением.

el() сознательно не делает разницы между «задать начальное значение при создании узла» и «обновить уже существующий узел»: он вызывается только в момент создания, через setAttribute, и этого достаточно для всех нужд проекта — причину, по которой второй случай ему не требуется вовсе, разберём в конце раздела упражнений этой главы и подробнее — в главе про рендер без Virtual DOM.

Отсутствие значения как выключатель

Любой генератор разметки — независимо от конкретной технологии — сталкивается с одной и той же задачей: как выразить «этот атрибут или этот узел присутствует только при определённом условии», не заводя для каждого такого случая отдельную развилку кода. Разные системы решают её по-разному, но решение почти всегда сводится к одной идее: особое, заведомо «пустое» значение трактуется как явный сигнал «пропустить». В JSX это {condition && <Badge />} — React не рисует вообще ничего, если выражение слева от && ложно, потому что false/null/undefined как дитя компонента интерпретируются как «здесь ничего нет»; у Vue для той же цели существует отдельная директива v-if; библиотека classnames, повсеместная в React-коде, строит строку CSS- классов из объекта, выкидывая те ключи, чьё значение ложно.

el() воспроизводит эту же идею самым экономным из возможных способов — без отдельного синтаксиса, директивы или библиотеки, а простой проверкой в начале обоих циклов внутри одной и той же функции:

// цикл по атрибутам (el(), строка 55)
if (v == null || v === false) return;
...
// цикл по детям (el(), строка 64)
if (kid == null || kid === false) return;

Один и тот же приём, повторённый дословно в двух разных местах одной функции, избавляет от отдельного «if»-хелпера на каждый условный атрибут или условного ребёнка по всему остальному коду: el('button', { disabled: index === 0 ? false : true }) пропускает атрибут при false без дополнительной развилки, а el('div', {}, cond && el('span', ...)) безопасно «не рисует» <span>, если cond ложно, — потому что false && x в JavaScript вычисляется в false, то самое значение, которое цикл по детям уже умеет пропускать. Эта вторая форма — условный рендер ребёнка через && — используется по всему проекту ровно в том виде, в каком это принято и в JSX-коде: синтаксис здесь другой (обычный JS, а не разметка), но решаемая задача и выбранный приём — те же самые.

2. Разбор кода 

var el = function (tag, attrs) {
  var node = document.createElement(tag);
  attrs = attrs || {};
  Object.keys(attrs).forEach(function (k) {
    var v = attrs[k];
    if (v == null || v === false) return;
    if (k === 'class') node.className = v;
    else if (k === 'html') node.innerHTML = v;
    else if (k === 'dataset') Object.assign(node.dataset, v);
    else if (k.slice(0, 2) === 'on' && typeof v === 'function') node.addEventListener(k.slice(2), v);
    else if (v === true) node.setAttribute(k, '');
    else node.setAttribute(k, v);
  });
  [].slice.call(arguments, 2).forEach(function append(kid) {
    if (kid == null || kid === false) return;
    if (Array.isArray(kid)) return kid.forEach(append);
    node.appendChild(kid.nodeType ? kid : document.createTextNode(String(kid)));
  });
  return node;
};

Разбор по веткам атрибутов:

  • class → node.className = v, а не setAttribute('class', v) — потому что class зарезервированное слово в object-literal ключах не является (это просто строка), но сам DOM предлагает удобное свойство className для той же цели, и по коду читается ровнее, чем setAttribute.
  • html → node.innerHTML = v — единственный путь вставить произвольный HTML напрямую, минуя дерево el()-вызовов (используется, например, для вставки SVG-иконок как готовых строк — см. view-common.js::SEARCH_SVG и подобные). Потенциальная XSS-дверь, если v когда-нибудь будет содержать пользовательский ввод — в ds-webui html используется только со статическими, захардкоженными строками (иконки), не с данными.
  • dataset → Object.assign(node.dataset, v) — dataset сам по себе особый DOM-объект (data-* атрибуты как свойства: node.dataset.ridx ↔ атрибут data-ridx), el() просто копирует туда поля целиком.
  • k.slice(0,2) === 'on' + функция → addEventListener. Заметь: не node[k] = v (т.е. не node.onclick = fn, “старый” способ назначить ровно ОДИН обработчик), а addEventListener — можно (в теории) навесить несколько обработчиков одного типа, хотя в этом проекте el() вызывается на каждый узел ровно раз, так что это отличие здесь не проявляется на практике.

Для вариативных детей (строка 63) — [].slice.call(arguments, 2) достаёт все аргументы после первых двух (tag, attrs) как настоящий массив (arguments сам по себе не Array, у него нет .forEach). Рекурсивная append разворачивает вложенные массивы (el('ul', {}, items.map(renderItem)) — результат .map это массив <li>, append сам пройдётся по нему рекурсивно).

Живой пример использования — view-table.js::cellNode 

var cellNode = function (v, entity, unparsed) {
  var attrs = ...;
  if (v === null) { attrs.class = 'del'; attrs.title = 'удалено (DELETE)'; return el('td', attrs, '∅'); }
  ...
  return el('td', attrs, String(v));
};

Видно всё сразу: attrs.class/attrs.title — обычные атрибуты через ветку else node.setAttribute(k, v) (title не попадает ни в одну специальную ветку); '∅'/String(v) — текстовый узел ребёнка, созданный автоматически (kid.nodeType ложно для строки → document.createTextNode(String(kid))).

Затем найдите (или временно создайте через Console: document.createElement ('input'), задайте setAttribute('value','a'), добавьте в DOM) инпут и проверьте разницу .value / .getAttribute('value') после ручного ввода текста в это поле — живое подтверждение упражнения 2.2.

2.6 — “Edit as HTML”. В Elements кликните правой кнопкой по любому <td> → Edit as HTML → впишите другой текст внутрь. Изменение видно немедленно. Теперь кликните по пиктограмме сортировки в заголовке того же столбца (это вызовет dispatch → полный ререндер грида). Что случилось с вашей ручной правкой? Объясните, почему (подсказка: та самая “полная перестройка поддерева”, глава 6).

5. Rust-трек

У Rust нет встроенного DOM (сам язык ничего не знает о браузере — это задача web-sys/wasm-bindgen, увидим в главе 10). Поэтому в этой главе — не “перепишите el() чтобы он управлял настоящим DOM”, а воспроизведите паттерн на чистых данных: постройте в Rust дерево узлов как структуру данных (без браузера вообще), с условной логикой атрибутов как в el().

enum AttrValue { Str(String), Bool(bool), Null }

struct Node {
    tag: String,
    attrs: Vec<(String, AttrValue)>,
    children: Vec<Node>,
}

fn el(tag: &str, attrs: Vec<(&str, AttrValue)>, children: Vec<Node>) -> Node {
    let filtered = attrs.into_iter()
        .filter(|(_, v)| !matches!(v, AttrValue::Null) && !matches!(v, AttrValue::Bool(false)))
        .map(|(k, v)| (k.to_string(), v))
        .collect();
    Node { tag: tag.to_string(), attrs: filtered, children }
}

Задание: допишите fn render_attrs(node: &Node) -> String, печатающую атрибуты как в HTML — с тем же правилом “булев true → пустая строка атрибута” (match по AttrValue, как el()’s if (v === true)). Обратите внимание, насколько match на enum в Rust делает невозможным забыть один из случаев (компилятор откажется собирать код, если вы не обработали AttrValue::Str — это “exhaustiveness checking”, которого у JS if/else if нет вообще).
